# Сайт rentos365.app — как с ним работать

Маркетинговый сайт продукта RentOS. Отдельная сущность от приложения: WordPress на общем VPS,
Elementor Pro 4.2 + Ultimate Addons for Elementor Pro, правится через MCP-сервер
`emcp-rentos365-app`. Приложение живёт на `my.rentos365.app` и к этим правилам отношения не имеет.

## Железные правила

**Никакого Custom CSS.** Требование пользователя, подтверждённое дважды. Всё оформление —
через штатные контролы виджетов, чтобы правилось из панели Elementor. Единственное
согласованное исключение: правило в CSS шапки (post 44), которое ставит две последние кнопки
меню в одну строку на мобильном — иначе это недостижимо. Новые исключения только с явного
разрешения, спрашивай отдельно.

**Никакого своего JavaScript.** По той же причине. Если эффект требует скрипта (симуляция,
бегущая строка, счётчики) — предложи альтернативу: запись экрана в виджет «Видео»,
статичный ряд, штатную карусель.

**Не менять шрифт и глобальные цвета.** Они настроены в Elementor и используются всем сайтом.

  в `src/app/api/auth/register/route.ts`. Пакет на триале — Free: 1 точка, 2 зоны,
  10 активов, 3 сотрудника.

  Pro $29, Max $69 в месяц.
- **Пять режимов учёта**: Счётчики, Пуски, Прибывания, Билеты, Только касса.

- Валюту в примерах не указывай или бери доллары: сайт международный.

## Грабли, на которые уже наступали

**Ссылки на глобальные цвета.** Хранятся отдельной картой, а не суффиксом в имени поля.
Правильно: `{"background_color": "#070050", "__globals__": {"background_color": "globals/colors?id=primary"}}`.
Форма `background_color__globals__` записывается, но Elementor её молча игнорирует — цвет не применится.

**WP Rocket отдаёт кэш.** После любой правки чисти, иначе проверяешь старую страницу и делаешь
неверные выводы (уже трижды приводило к ошибочным диагнозам):
`ssh -i ~/.ssh/id_rentos_vps md33@194.156.65.114 "rm -rf /var/www/md33/data/www/rentos365.app/wp-content/cache/wp-rocket/rentos365.app/*"`
Кэш **отдельный на каждый язык** TranslatePress и генерируется в разные моменты. Симптом
«на русском не работает, переключил на английский и обратно — заработало» означает не разницу
языков, а то, что одна из копий сделана до правки. Сверяй `Debug: cached@<ts>` в хвосте HTML.

**Кэш браузера у пользователя — третий слой, и он самый вредный.** HTML главной отдаётся
вообще без заголовков кэширования: ни `Cache-Control`, ни `ETag`, ни `Last-Modified`. Браузер
решает сам и держит копию часами (2026-08-07 так «не применилась» замена видеовиджета —
на самом деле Opera на телефоне показывала старую страницу). Прежде чем перепроверять
разметку, дай пользователю ссылку с мусорным параметром — `https://rentos365.app/?nocache=1`.
Она проходит мимо WP Rocket (тот не кэширует URL с незнакомой строкой запроса) и мимо кэша
браузера сразу. Чинится mu-плагином, который шлёт `Cache-Control: no-cache, must-revalidate`
на HTML-ответы, — пока не сделано.

**Виджет Video из Ultimate Addons ломает self-hosted видео.** UAEL 1.45.3: для `video_type=hosted`
разметка плеера кладётся в атрибут `data-hosted-html` **дважды экранированной** — `\"класс\"`,
`&quot;` вместо кавычек, `<\/video>`. Скрипт вставляет эту строку в DOM, браузер её не парсит,
и на странице не оказывается ни одного `<video>` вообще (2026-08-07, главная). Настройками
не лечится. Для своих файлов бери **штатный «Видео» Elementor** — он отдаёт нормальный
`<video autoplay loop muted playsinline>` прямо в HTML, без JS. UAEL-виджет годится только
для YouTube/Vimeo.

**Проверять видео и прочий JS-зависимый DOM — только реальным браузером.** `curl` показывает
исходный HTML, а не то, что осталось после скриптов. Headless Chrome по CDP: node-скрипт
поднимает `chrome.exe --headless=new --remote-debugging-port=…`, дальше `Runtime.evaluate`
на `document.querySelectorAll('video')` и на `paused/readyState/error` элемента.
Так и нашли причину выше.

**Разметка в пунктах меню срезается.** Через `menu-write` HTML в названии пункта не сохраняется —
WordPress санитайзит. Пользователь вставляет её сам в Внешний вид → Меню, где у него есть право
на HTML. Готовь ему строку для вставки, не пытайся записать сам. И не трогай потом эти пункты
через API — правка обнулит разметку.

**Pro-виджеты.** `add-pro-widget` по умолчанию выключен в EMCP Tools → Tools. Если нужен
`nested-tabs`, `form`, `call-to-action` — попроси включить и переподключить MCP.

**Сетки.** В `grid_columns_grid` обязательно передавай `sizes: []`, иначе размер игнорируется
и колонок будет две по умолчанию.

**Заголовок страницы от темы.** Hello печатает `<h1 class="entry-title">` в `.page-header` —
при своём H1 на странице получается дубль. Скрывается штатной настройкой Elementor,
пользователь делает это сам.

**og:image.** Заглушка Elementor в хиро подхватывалась как картинка для репостов. Проверяй
`<meta property="og:image">` после публикации. Запасная картинка на весь сайт задана в
`wpseo_social.og_default_image`.

**Отступы меню связаны.** Вертикальный отступ пунктов выпадающего списка задаёт и расстояние
между пунктами, и белое поле под последним. Развести можно нижней рамкой панели, покрашенной
в цвет фона — рамка к пунктам не привязана.

**Хлебные крошки на главной.** Yoast выводил там `BreadcrumbList` из одного элемента без ссылки,
Google рапортовал «Отсутствует поле itemListElement» в Search Console. Починено mu-плагином
`wp-content/mu-plugins/rentos-front-breadcrumb.php`: на главной убирается и сам блок
(`wpseo_schema_graph_pieces`), и ссылка на него из узла страницы (`wpseo_schema_webpage`).
На остальных страницах крошки не тронуты. Инструмента для PHP-сниппетов в EMCP нет —
`add-code-snippet` умеет только CSS и JS, поэтому такие правки ставятся mu-плагином по SSH.

**Ищешь JSON-LD регуляркой — учитывай пробелы.** На переведённых страницах разметка выводится
форматированной (`"@type": "BreadcrumbList"` с пробелом после двоеточия), на русской —
минифицированной. Поиск без `\s*` даёт ложное «разметки нет».

## WP Rocket — что включено и почему (2026-08-07)

Настройки лежат в опции `wp_rocket_settings`, правятся `wp eval` + `update_option` (у плагина
нет своей wp-cli команды). Бэкап актуального состояния — `~/wp-rocket-settings-backup-20260807.json`
на сервере. После правки чистить и `cache/wp-rocket/`, и `cache/min/`.

Включено: `minify_css`, `minify_js`, `defer_all_js` (jQuery в `exclude_defer_js`, иначе рвутся
инлайновые `jQuery(...)`), `delay_js` + `delay_js_execution_safe_mode`, `lazyload`,
`lazyload_css_bg_img`, `lazyload_iframes`, `image_dimensions`, `auto_preload_fonts`,
`host_fonts_locally`, `manual_preload`, `preload_links`, `cache_mobile`, `control_heartbeat`.

**`remove_unused_css` и `async_css` не включать — они мертвы на этом сайте.** Обе с версии 3.11
считаются в облаке WP Rocket. Проверено: очередь из 9 задач отработала, `cache/critical-css/1/`
осталась пустой, таблица `wp_wpr_rucss_used_css` пуста. Настройка включается, но не делает
ничего — а в таком виде она опаснее выключенной, потому что может однажды применить
недосчитанный CSS без свидетелей.

**`delay_js` в safe mode откладывает ровно один скрипт — gtag.** Всё остальное safe mode
исключает. Значит визуально ничего не ломается, но **просмотры от посетителей, ушедших без
единого действия, в аналитику не попадут**. Это осознанный размен, не забывать про него,
когда владелец спросит, почему просело число сессий.

**`lazyload_youtube` (замена iframe картинкой) не трогать** — ломает вид встроенных видео.
На `<video>` ленивая загрузка WP Rocket не распространяется вообще, hero-видео ей не мешает.

Проверять правки скриптом `audit.js` (headless Chrome по CDP), а не глазами: он снимает
состояние видео, `slick-initialized`, канвасы частиц, число пунктов меню, sticky-шапку,
`cssRules`, `scrollHeight`, ошибки консоли и упавшие запросы — и это сравнивается с базой
до правки. Так партии настроек проверялись по одной.

## Переводы (TranslatePress)

Пять языков: `ru_RU` (базовый), `en_US`, `uk`, `it_IT`, `ro_RO`. Слаги в URL — `ru/en/ua/it/ro`
(украинский именно `ua`, не `uk`). Строки регистрируются САМИ при первом рендере страницы,
переводы лежат в `wp_trp_dictionary_ru_ru_<lang>`: `original`, `translated`, `status`
(0 — нет, 1 — машинный, 2 — проверенный), `original_id`.

**Переводим текстом сами, статусом 2. Машинный перевод не включать.** Ключ DeepL в опции
`trp_machine_translation_settings` прописан, но `machine-translation: no` — и так и надо.
Проверено 2026-08-07: DeepL ломает ровно продуктовые термины — «Пуски» стали *Single-use* (en)
и *Biglietti singoli* (it), а последнее сталкивается с *Biglietti* = Билеты.

Глоссарий (брать из базы, `WHERE status=2`, а не выдумывать):

| ru | en | uk | it | ro |
|---|---|---|---|---|
| Счётчики | Counters | Лічильники | Contatori | Contoare |
| Пуски | Launches | Заїзди | Corse | Curse |
| Прибывания | Stays | Перебування | Soggiorni | Șederi |
| Билеты | Tickets | Квитки | Biglietti | Bilete |
| Только касса | Cash only | Лише каса | Solo cassa | Doar casă |
| Товары | Products | Товари | Prodotti | Produse |
| Сдача итогов | Results submission | Здача підсумків | Chiusura di giornata | Închiderea zilei |

Порядок: (1) отрендерить страницу, чтобы строки зарегистрировались; (2) выгрузить их скриптом
(сопоставление «строка принадлежит статье» — поиском подстроки в `post_content`); (3) написать
переводы в JSON `{enTableId: {en,uk,it,ro}}`; (4) применить PHP-скриптом, который ищет строку
в каждой языковой таблице **по `original`, а не по id** — id в таблицах разные. Готовые скрипты
экспорта и применения — в истории сессии 2026-08-07.

### Список «что осталось перевести» из словаря — врёт

TranslatePress копит оригиналы НАВСЕГДА. Переписали текст страницы — прежние формулировки
остаются в словаре и выглядят непереведёнными. На «Возможностях» 2026-08-09 из 93 «непереведённых»
строк живыми оказались 37, а 56 были остатками прежних версий, включая строительные заметки автора
(`[ЯКОРНОЕ МЕНЮ — сделать sticky вручную…]`, `1. HERO`, `см. гайд`). Перевод словаря целиком —
половина работы в мусор.

**Мерить по отрендеренной странице, а не по словарю.** Два приёма:

- быстрый: взять текстовые узлы страницы на нужном языке и отобрать те, где остались русские
  буквы. Для `/ua/` так нельзя — украинский тоже кириллица; там ищутся `ъ ы э ё` и характерные
  русские слова;
- точный: сравнить текстовые узлы русской версии и языковой. Узел, совпавший ДОСЛОВНО, —
  непереведённый. Ловит и украинский, и строки без «русских» признаков. Ложные срабатывания —
  строки, чей перевод совпадает с оригиналом («Блог», «Магазин», «Батут», «Браслет №7» по-украински
  пишутся так же); проверять по словарю: если `translated` непуст и равен оригиналу — всё в порядке.

### Заголовок страницы — отдельная строка от названия

Yoast склеивает название с названием сайта, и для TP «Аккаунт» и «Аккаунт - RentOS 365» — разные
оригиналы. Первый бывает переведён, второй нет — тогда вкладка браузера и выдача поиска остаются
русскими при полностью переведённой странице (2026-08-08). Разделитель к тому же однажды менялся
(`—` на `-`), поэтому старые заголовки с тире в словаре мертвы.

### Уборка словаря: единственное безопасное условие

Удалять запись можно, только если **перевод пуст во всех четырёх языках**. Тогда терять нечего:
если набор живых строк оказался неполным, TP зарегистрирует строку заново при следующем показе.
Есть хоть один перевод — не трогать, даже если строки на сайте больше нет.

Набор живых строк собирается обходом карты сайта (`{post,page,docs,fluent-products,category,
doc_category}-sitemap.xml`, русские адреса — оригиналы русские) и должен включать:

- **весь документ, а не `<body>`/`<main>`** — заголовки и описания живут в `<head>`;
- **значения атрибутов** `alt`, `title`, `placeholder`, `aria-label`, `content` и адреса картинок:
  TP переводит и их;
- **страницы-приложения, снятые браузером** — витрина, корзина, кабинет, портал поддержки.
  В HTML их содержимого нет вовсе.

Первый заход 2026-08-09 собирал только текст из `<body>` — и в «мёртвые» попали живые заголовки
страниц, alt-подписи и вся витрина. Итог уборки: 762 мёртвых строки и 115 дублей на ~3200 записей.
Перед удалением — `wp db export` словарей и `trp_original_*`.

**Дубли** (несколько записей одного оригинала в одной таблице) — оставлять ту, где есть перевод,
при равенстве меньший id.

**Слаги переводятся отдельно**, таблицы `wp_trp_slug_originals` / `wp_trp_slug_translations`.
Автоперевод слагов включён и на кириллице выдаёт процентную кодировку
(`%d0%be%d0%b1%d0%bb%d1%96%d0%ba-...`) — для украинского обязательно подменять транслитерацией
вручную. Требование пользователя: слаг на своём языке, но латиницей.

**Проверять языковые версии только через `curl -sL`** — без `-L` прилетает 301 на переведённый
слаг, страница не рендерится, и кажется, что перевод не сработал (потерял на этом заход).

**Названия языков в переключателе остаются на своём языке** (`native_or_english_name: native_name`) —
«Русский» и «Українська» на английской странице это не непереведённые строки. Ссылки переключателя
ОБЯЗАНЫ вести на другие языки, поэтому при проверке ссылок его надо вырезать по разметке
(`trp-language-switcher`, `trp_ald_*`), иначе он даёт ложную тревогу на каждой странице. Ссылка на
`/` в теле переведённой страницы — это тоже он, всплывашка автоопределения языка.

### Слаги: сплошная проверка

Требование владельца: **ни кириллицы, ни процентной кодировки** — ни в `post_name`, ни в переводах
слагов. Проверять оба места; на 2026-08-09 нашлось по одной беде в каждом:
`[uk] prices → %d1%86%d1%96%d0%bd%d0%b8` (это «ціни») и товар `Starter → %d0%bf…-starter`.
Оба были в карте сайта, то есть их видел Google. Плагин `cyr2lat` транслитерирует только НОВЫЕ
слаги, старые остаются как есть.

Искать ссылки на такой слаг **только через `esc_like`**: знак процента в LIKE это подстановка, и
«сырой» шаблон `%d0%bf%d0%bb%` совпадает почти с чем угодно — первый заход так дал ложные 83
совпадения.

Внутренний слаг `elementor_library` («Набор по умолчанию») трогать незачем — это набор стилей, а не
адрес страницы.

## Плагины Fluent — как переводить

Стоят девять: FluentCart + Pro + Elementor Blocks, Fluent Forms, PDF Generator, FluentSMTP,
Fluent Support + Pro, FluentAuth, FluentHub. Локаль сайта `ru_RU`.

**Механизм — только .po/.mo, и он покрывает фронтенд.** Проверено 2026-08-07: ни один плагин
Fluent не вызывает `wp_set_script_translations`, то есть штатного JS-механизма перевода у них нет.
Вместо этого строки Vue-приложений объявлены обычными `__()` в PHP-файлах
(`app/Services/Translations/checkout-translation.php`, `customer-profile-translation.php`,
`admin-translation.php`) и уходят в JS уже переведёнными. Значит `.mo` достаточно, JSON не нужен.

Домены: `fluent-cart`, `fluent-cart-pro`, `fluent-cart-elementor-blocks`, `fluent-security`,
`fluent-support`, `fluent-support-pro`, `fluent-toolkit`, `fluentform`.

Пакеты с translate.wordpress.org (GlotPress) прилетают сами и лежат в
`wp-content/languages/plugins/`. Есть для `fluent-cart`, `fluentform`, `fluentforms-pdf`,
`fluent-smtp` — все на 100%. **У Pro-версий пакетов нет и не будет**: их нет на wp.org.
Официальная инструкция ([docs.fluentcart.com](https://docs.fluentcart.com/guide/customization-and-themes/translating-fluentcart))
— делать через Loco Translate и обязательно сохранять в **Custom**-расположение
`wp-content/languages/loco/plugins/`, иначе перевод сотрёт обновлением плагина.

**Главная ловушка: не всё английское на витрине — это строки плагина.** FluentCart при установке
создаёт страницы Shop/Cart/Checkout/Account и записывает в контент страницы «Shop» шаблон
гутенберг-блока с ЗАХАРДКОЖЕННЫМИ английскими метками фильтров (`"label":"Product Categories"`,
`"label":"Product Brands"`, `"label":"Price"`, «No results found», «clearing any filters»).
В `app/CPT/Pages.php` ноль вызовов `__()` — это не переводимые строки, а содержимое страницы
в базе. Переводится правкой контента страницы, никакой .po не поможет. Заголовки самих страниц —
тоже обычные `post_title`, переименовываются как любая страница. Сделано 2026-08-07: Магазин /
Корзина / Оформление заказа / Личный кабинет.

Проверять результат отрендеренным DOM, а не `curl`: витрина и кабинет — JS-приложения. Headless
Chrome по CDP, обязательно с настольным вьюпортом (`Emulation.setDeviceMetricsOverride`, 1400×900):
в узком окне меню кабинета скрыто вёрсткой, и все размеры и часть строк просто отсутствуют — легко
пойти искать поломку, которой нет.

**Слаги товаров переименовывать МОЖНО** (уточнено 2026-08-09, прежняя формулировка «не трогать» была
осторожнее, чем нужно). Покупка идёт по числовому id вариации: кнопки на «Ценах» ведут на
`/?fluent-cart=instant_checkout&item_id=<id вариации>` — `item_id` 1..6 это Starter/Pro/Max ×
Ежемесячно/Ежегодно. Подписки и заказы ссылаются на `product_id`/`variation_id`, корзины — на
`post_id`. WordPress сам ставит 301 со старого слага. Проверять до и после: все шесть
`instant_checkout` (302 на `/checkout/?fct_cart_hash=…`), состав корзины, и браузером — что живая
подписка и история покупок в кабинете на месте.

**Подписи вариаций в кабинете заморожены одной строкой.** `fct_subscriptions.item_name` =
«Max - Ежегодно», `fct_order_items.title` то же — FluentCart сохраняет их при покупке. TP сверяет
текстовый узел целиком, поэтому перевода слова «Ежегодно» недостаточно: нужны все подписи и все
разделители (`-`, `–`, `—`). Динамический переводчик TP (`trp-translate-dom-changes.js`) до кабинета
ДОТЯГИВАЕТСЯ — проверено, подписи переводятся. Имена тарифов переводить нельзя: на украинском
«Max» однажды стал «Макс».

**Иконки пунктов меню кабинета чистятся `wp_kses`** со списком `fct_allowed_svg_tags`. В нём
`viewBox` записан в смешанном регистре, а kses приводит имена атрибутов к нижнему — атрибут
вылетает ВСЕГДА, и рисунок из сетки 24 обрезается до 20. Нет и `stroke-linecap`. Лечится не
пересчётом иконки, а дополнением списка своим фильтром (приоритет 20, ключи строчными). Тогда
Lucide берётся как есть из `spectre-icons/assets/iconpacks/lucide/`.

**Loco Translate установлен 2026-08-07** (v2.8.8) — по рекомендации Fluent. Важно: путь
`wp-content/languages/loco/plugins/` подключает сам Loco, без него он мёртвый; штатный
`wp-content/languages/plugins/` работает всегда. Пакеты с wp.org ставить так:
`wp language plugin install <slug> ru_RU`. Так поставлен `fluent-security` (575 строк, 100%) —
после установки все английские подписи формы регистрации стали русскими сами.
`fluent-support` уже стоял (1836 строк, 100%).

Решение владельца 2026-08-09: **Loco оставляем** (Fluent его рекомендует, и это единственный способ
править эти файлы без SSH). Копии `.mo` продублированы в штатный путь ядра, так что выключение Loco
переводы больше не убьёт — проверено снятием его фильтра `load_textdomain_mofile`. Обратная сторона:
пока Loco активен, работает ЕГО копия. Поправите строку через его панель в расположение Custom —
штатная копия молча устареет, и нужно её обновить. Справочные `.po` лежат в репозитории приложения:
`wordpress/languages/`.

Проверяя «доживёт ли перевод без Loco», обязательно `unload_textdomain($domain, true)` со вторым
аргументом: без него домен помечается выгруженным до конца запроса и обратно не загружается —
проверка даёт ложное «перевод потеряется» для всех языков, кроме первого.

**Вторая ловушка, важнее первой: строка переведена в .po, но на витрине английская.**
Значит это ЗНАЧЕНИЕ НАСТРОЙКИ, а не живой вызов `__()`. Плагины Fluent строят дефолты через
`__()` и один раз сохраняют результат в базу — дальше перевод к ним не применяется никогда.
Найдено дважды:
- Fluent Support: `wp_fs_meta.key = 'global_business_settings'`, поле `login_message`.
  Значение **PHP-сериализовано** — править только через `unserialize` → правка → `serialize`,
  `str_replace` по сериализованной строке ломает длины.
- FluentAuth: опция `__fls_auth_customizer_settings` — восемь полей (`login`/`signup` ×
  `banner.title`, `form.title`, `form.button_label`, `form.description`).

Диагностика: если `wp eval` показывает, что `__($s, $domain)` возвращает русский, а на странице
английский — ищи строку по ВСЕМ таблицам (перебор `SHOW COLUMNS` + `LIKE`), она осела в настройках.

Мелочь: в `wp eval` не писать `«$var»` — PHP цепляет `»` к имени переменной и роняет
предупреждение. Использовать конкатенацию.

**TranslatePress здесь не помощник, и это важно понимать.** Он переводит ТОЛЬКО с языка
по умолчанию на остальные. По умолчанию русский — значит английский текст от плагина для TP
не «непереведённое», а исходник, переводить его некуда. Поэтому английские строки плагинов
живут на сайте сколько угодно, несмотря на работающий TranslatePress. Лечится только
языковым пакетом, правкой настройки или фильтром. Плюс на `wp-login.php` TranslatePress
не работает вообще (проверено — ноль его разметки); переключатель языка там штатный, от ядра,
и меняет локаль WP через `wp_lang`.

**Украинского, итальянского и румынского у плагинов Fluent на wp.org НЕ СУЩЕСТВУЕТ** — их нет
даже в списке доступных (`wp language plugin list <slug>`). Есть только: у fluent-security —
ja/ko/nl/pt_BR/ru/sk/vi, у fluent-cart — es/ko/lo/nl/ru/sk/zh, у fluent-support —
de/es/fa/fr/ja/ko/nl/ru/sk/tr. Русский есть везде, три языка сайта — нигде. Скачивать нечего,
только делать самим.

Практика 2026-08-08: на экране входа реально видны всего **пять** строк FluentAuth
(`Your Full Name`, `Password`, `Re-Enter Password`, `I agree to the terms and conditions`,
`Reset Password`). Под них собраны частичные .po/.mo на uk/it_IT/ro_RO — недостающие строки
gettext отдаёт как msgid, это нормально, весь пакет переводить не требуется.
Компиляция: `wp i18n make-mo file.po .` (msgfmt на сервере нет, wp-cli умеет).
Положены в `wp-content/languages/loco/plugins/` — **проверено, Loco этот путь действительно
подключает**, `LOCO_LANG_DIR` определён.

Диагностика по «сколько осталось английского»: не фильтровать по латинице — итальянский
и румынский тоже латиница, и `Accedi`, `Nome utente`, `Ai uitat parola?` попадут в ложные
срабатывания. Проверять точечным списком конкретных msgid.

**Строки плагинов TranslatePress НЕ переводит, даже если завёл их в словарь.** Проверено
2026-08-08 на `/it/shop/`: записи в `wp_trp_dictionary_*` стояли со статусом 2 и корректным
переводом («View Options» → «Vedi opzioni»), а на странице оставался английский. Вывод плагина
помечен `data-no-translation` (46 маркеров на странице), TP его пропускает. Переводится
контент страницы и заголовки — но не то, что отрендерил плагин. Значит правило: **строку лечить
там, где она родилась** — контент правим в контенте, строки плагина в .mo. Записи в словаре TP
для таких строк безвредны, но бесполезны.

Готовые частичные пакеты на uk/it_IT/ro_RO лежат в `wp-content/languages/loco/plugins/`:
`fluent-security-*` (5 строк экрана входа), `fluent-cart-*` (Search products, Minimum/Maximum
price, View Options, Login, Please log in to access your customer portal.),
`fluent-support-*` (Not registered?, Create an account, Forgot your password?, Reset password).
Появится новая английская строка — дописать msgid в соответствующий .po и пересобрать
`wp i18n make-mo file.po .`.

**«Change Language» / «Close and do not switch language» останутся английскими** — это значения
настроек самой TranslatePress (`trp_ald_settings`: `popup_textarea`, `popup_textarea_button`,
`popup_textarea_close_button`), и она НЕ регистрирует их в собственном словаре (проверено).
Одно значение на все языки. Всплывашка показывается посетителю, чей язык браузера отличается
от языка страницы, — английский там разумнее любого одного из пяти.

**Тексты экрана входа FluentAuth не переводимы в принципе** — в `app/Helpers/Helper.php`
дефолты заданы голыми строками без `__()` (`'title' => 'Welcome to ' . $siteTitle`). Очистка
настройки вернёт английский, а не переводимый вариант. Решено mu-плагином
`wp-content/mu-plugins/rentos-fluentauth-i18n.php` (2026-08-08): цепляется за core-фильтр
`option___fls_auth_customizer_settings` и подменяет четыре поля по `determine_locale()`.
Своего хука у плагина нет, но у ЛЮБОЙ опции WP есть фильтр `option_<имя>` — это чистый путь,
файлы плагина не трогаются и обновление их не сотрёт. В админке фильтр отключён (`is_admin()`),
иначе настройки FluentAuth стали бы нередактируемыми из панели.

## Медиа

Видео на сайте — реальная съёмка точек (игровые комнаты), а не запись экрана: мелкая сетка,
канаты, движение камеры. Сжимается плохо, целиться в «пару мегабайт» на 720p бесполезно.
Рабочий рецепт для hero-петли (2026-08-07, `uploads/2026/08/rentos1.mp4`, 42 с → 3,2 МБ):

```
ffmpeg -i in.mp4 -an -vf "scale=854:480:flags=lanczos" -c:v libx264 -preset veryslow -crf 32 \
       -profile:v main -level 4.0 -pix_fmt yuv420p -movflags +faststart -g 50 out.mp4
```

854×480 хватает: контейнер hero — 50% от 1140, на экране бокс ~674 px. Оригинал остаётся
рядом на сервере как `*.orig-backup.mp4`. `ffmpeg` лежит локально в
`D:\!Claude - DONT TOUCH\tools\ffmpeg\`, на VPS его нет.

Файл подменяется по SSH поверх старого (URL и attachment ID не меняются), после чего надо
пересчитать метаданные вложения, иначе в медиатеке останутся старые размер и разрешение:
`wp eval 'require_once ABSPATH."wp-admin/includes/image.php"; wp_update_attachment_metadata($id, wp_generate_attachment_metadata($id, get_attached_file($id)));'`

nginx не отдаёт на `/wp-content/uploads/*.mp4` никакого `Cache-Control` — браузер кэширует
эвристикой. Правится только в конфиге vhost, не через WP.

**Картинки к статьям блога.** Формат один на весь блог — 1200×675 (16:9), `.jpg`, одна и та же
картинка идёт и в обложку (`featured_image`), и блоком `wp:image` сразу после первого абзаца.
`search-images` не работает — стоковый провайдер в EMCP → Connection не подключён, ключа нет.
Но `sideload-image` ключа НЕ требует: ищи фото через WebSearch, забирай прямой URL через
WebFetch со страницы фото и передавай его в `sideload-image` (Pexels — свободная лицензия,
можно коммерчески и без атрибуции). Ставь `convert_webp: false`, иначе выбьешься из общего
формата — весь блог на `.jpg`. Размер задаётся параметрами Pexels: `?auto=compress&cs=tinysrgb&w=1200&h=675&fit=crop`.

## Порядок работы

1. **Перед сборкой страницы** загрузи `get-skill("emcp-skills")`, а при работе с компонентами
   и отладкой вёрстки — ещё `emcp-skills/recipes` и `emcp-skills/audit`. Там готовые рецепты
   карточек и разбор ловушек флекса, не изобретай заново.
2. **Перед переписыванием страницы** сделай бэкап: `export-content` с её `post_id`.
3. **Собирай посекционно**, не одним вызовом `build-page`.
4. **Проверяй результат по скомпилированному CSS** (`/wp-content/uploads/elementor/css/post-<ID>.css`),
   а не по факту записи настройки — часть настроек молча не применяется.
5. **Проси референс.** Описания словами вроде «современно и ярко» дают плохой результат;
   разбор конкретной страницы — хороший.
